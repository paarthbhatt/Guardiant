# Guardiant security audit — 2026-10-11

## Scope and methodology

This was a source-level pre-ship audit of the Guardiant scanner core and its
local delivery surfaces. The review covered:

- `apps/cli`: command parsing, scan lifecycle, local configuration, database
  persistence, analytics calls, and report output.
- `packages/core`: orchestration, filesystem indexing, URL scanning, active
  exploit replay, LLM prompts and consumers, fix generation, YAML rules, and
  report formatting.
- `packages/shared`: scan/report types, analytics, HTTP utilities, and secret
  redaction helpers.
- `packages/database` and `packages/queue`: persistence, job payloads, and
  query boundaries.
- `apps/web`, `Dockerfile`, CI configuration, package manifests, lockfile, and
  repository tests.

The audit followed the work-order sequence: injection and trust boundaries,
authentication/authorization, parsing and deserialization, runtime replay,
and supply chain. I traced data from CLI arguments, fetched pages, repository
files, findings, queue jobs, and LLM responses to their sinks. Exact searches
covered shell execution, dynamic code execution, HTML sinks, URL requests,
JSON/YAML parsing, provider calls, persistence queries, and telemetry.

Severity reflects the effect when Guardiant is run against an untrusted URL or
repository, with AI and active exploit mode treated as explicit deployment
options. No scan test was run against an external host; regression fixtures use
temporary local directories, symlinks, mocked providers, and mocked HTTP.

### Executive summary

Two high-impact trust-boundary gaps remain open and require design changes:

1. active replay does not yet enforce an authorized URL origin and egress
   policy; and
2. LLM text is still allowed to influence finding suppression and auto-fix
   code generation.

The persistence layer is also not tenant/user-aware. That is a deployment gap
for any future shared service, although the current product is a local CLI and
does not expose an authenticated API or MCP server.

The smaller, bounded issues found during the audit were fixed: shell argument
injection, repository path traversal and symlink escapes, unsafe YAML schema
handling, report/dashboard HTML injection, and response-body timeout cleanup.
Production dependency auditing is now clean: the final `pnpm audit --prod`
snapshot covers 290 production dependencies and reports zero advisories.

## Architecture and trust boundaries

### Components and entry points

1. `apps/cli/src/index.ts` registers Commander commands. `scan.ts` validates
   arguments, optionally creates the local SQLite record, calls the
   orchestrator, emits PostHog events when configured, and writes JSON,
   Markdown, HTML, or SARIF output.
2. `packages/core/src/orchestrator/orchestrator.ts:40-317` runs recon,
   classification, indexing, the static/LLM agent swarm, deterministic finding
   validation, LLM critic review, analysis, exploit generation, and fix
   generation.
3. URL agents use `packages/core/src/http/index.ts:68-153` and the web scanner.
   Recon fetches page-linked scripts and common paths. Active exploit mode
   replays requests generated from finding evidence.
4. Directory agents read source files and package manifests. The code index,
   critic, fix agent, suppression rules, and supply-chain agent all consume
   repository-controlled paths or content.
5. `packages/core/src/llm/client.ts` is the outbound provider boundary.
   Agent prompts include finding text, source snippets, route metadata, and
   scan targets. LLM responses become findings, critic verdicts, payloads, or
   proposed patches.
6. `packages/database/src/schema/index.ts` stores scans and all scan-owned
   records in SQLite. `packages/queue` can carry scan targets and recon data in
   Redis jobs. Neither layer currently carries an owner or tenant context.
7. `packages/core/src/report/formats/index.ts` produces standalone HTML and
   `apps/web/index.html` renders scan response data in the dashboard.

### Trust-boundary map

```text
CLI args / local path / URL
          |
          v
  scan-args -> ScanConfig -> Orchestrator
                              |
              +---------------+----------------+
              |               |                |
        repository files   HTTP fetches    findings/recon
              |               |                |
              +-------+-------+----------------+
                      v
                 agent prompts ----> LLM provider
                      |                    |
          findings / critic verdict   JSON / patch text
                      |                    |
              validator -> exploit replay / auto-fix
                      |                    |
                 SQLite / Redis / reports / dashboard
```

The dangerous crossings are repository or remote content into prompts,
finding-controlled URLs into HTTP replay, model output into code changes, and
scan records into persistence APIs without an authorization context.

## Top five must-fix details

### 1. G-01 — LLM prompt injection and model-authorized changes

**Impact.** A scan can process attacker-controlled repository comments, source
strings, HTML, routes, and finding evidence. Those values are concatenated into
LLM prompts. With `GUARDIANT_ENABLE_AI=1`, the model can return a critic verdict
or a patch. A syntactically valid malicious patch is not necessarily a secure
patch, and the current auto-fix path can apply a high-confidence response.

**Required design.** Keep deterministic scanner evidence authoritative. Make
critic output advisory and retain findings unless a deterministic validator
also supports suppression. Make generated patches review-only by default;
require an explicit human approval step for any application, validate that the
replacement is limited to the finding's source span, and reject changes to
security-sensitive files or authorization logic without review. Use strict
Zod schemas for every LLM response and cap prompt/context size.

**Current status.** The LLM is now explicitly opt-in and model responses are
bounded before becoming findings. The trust decision itself remains open and
is marked at `critic-agent.ts:54`, `fix-agent.ts:530`, and
`orchestrator.ts:462`.

### 2. G-02 — SSRF and uncontrolled active replay

**Impact.** Reconnaissance and exploit code can request URLs that originate in
remote HTML or finding evidence. `fetch` follows redirects, so an apparently
safe first hop can redirect to a private address. In active mode this can turn
the scanner into a network pivot; even passive recon can disclose response
data to a target chosen by the scanned application.

**Required design.** Derive an immutable authorized origin set from the CLI
target. Resolve DNS before connecting and reject loopback, RFC1918, link-local,
Unix-socket, and cloud-metadata destinations unless an explicit local-test
policy allows them. Revalidate redirect destinations and enforce method,
header, body-size, and request-count limits. Record the final destination in
evidence.

**Current status.** Timeouts are hardened, but destination authorization is
not implemented. The intended fix locations are marked at `http/index.ts:69`
and `exploit-agent.ts:100`.

### 3. G-03 — Missing tenant and authorization boundary

**Impact.** The current CLI is local, but the database and Redis job abstractions
look reusable as a service. They do not carry an owner or tenant, and query
functions accept only an ID or broad list options. A future API could therefore
expose one customer's source-derived findings to another customer.

**Required design.** Introduce an authenticated request context containing
tenant and user IDs. Store tenant ownership on scans and either derive child
ownership through joins or store it with foreign-key constraints. Require the
context in every operation, scope list/get/update/delete queries, and carry it
in queue payloads. Add negative cross-tenant tests before enabling a shared
deployment.

**Current status.** No MCP server or tenant-aware HTTP API was found in this
repository, so this is a release-blocking architecture requirement for a
shared service rather than an exposed local-CLI endpoint. The schema marker is
at `packages/database/src/schema/index.ts:7`.

### 4. G-04 — Repository hooks during auto-fix

**Impact.** The argument injection fix removes shell interpolation, but Git is
still an execution boundary. A repository can contain hooks that run as part
of `git commit`; `FixAgent` invokes that command when an applicable patch is
auto-applied.

**Required design.** Make patch generation and export the default. If a commit
is required for a controlled workflow, operate on a temporary clone with
hooks disabled and a sanitized Git configuration, then copy only the reviewed
diff back. Do not use `--no-verify` as the sole control because it does not
represent a complete hook isolation policy.

**Current status.** The remaining risk is explicitly marked at
`packages/core/src/agents/fix-agent.ts:834`.

### 5. G-05 — Telemetry data minimization

**Impact.** A configured PostHog key enables network telemetry. URL sanitization
removes query and fragment values but preserves hostname and path, which may
identify private applications or sensitive endpoints. Error text and arbitrary
feature metadata are also forwarded.

**Required design.** Define a small, documented event schema containing only
counts and coarse categories. Omit target values or replace them with a
user-local hash, redact error details, and reject arbitrary metadata keys.
Require explicit telemetry consent where appropriate and test that private
paths cannot be emitted.

**Current status.** Analytics remains opt-in through `POSTHOG_API_KEY`; the
redaction policy is not yet implemented. The marker is at
`packages/shared/src/analytics/index.ts:72`.

## Audit coverage and clean classes

### Injection and output handling

Prompt injection is **not clean**: hostile repository and remote content enters
LLM prompts, and model output influences verdicts, payloads, findings, and
patches (G-01). The generated HTML report and static dashboard had stored DOM
injection paths; those are fixed as G-06. Shell metacharacter injection into
the scanner's own Git/syntax-check commands is fixed as G-08, with repository
hook execution remaining as G-04.

### Authentication and authorization

No MCP server, authenticated HTTP API, or tenant-aware request boundary was
found. Provider API keys are read from environment/configuration and sent only
to the selected provider; no hard-coded credential was found in the reviewed
source. The local config command masks keys when displaying them. Shared-service
authorization and tenant isolation are absent from persistence and queue
models (G-03). No auth/secrets handling was changed because the audit did not
confirm a hard-coded credential or a missing authentication check in an
existing public API.

### Parsing and deserialization

JSON parsing is used for package files, HTTP response bodies, JWT header
inspection, and LLM responses. Most package/rule inputs are subsequently
validated or consumed as data. YAML rule loading now uses `yaml.JSON_SCHEMA`
and Zod validation (G-09). Generic orchestrator findings and fix-agent patch
responses still need stricter field-by-field validation as part of G-01.

The audit found no application use of `eval`, `new Function`, or `vm.run*` for
scan data. The Docker `--experimental-vm-modules` flag enables Node's module
loader mode; it is not a trace interpreter. There is no generic replay engine
that deserializes a trace into executable code.

### Runtime replay and subprocesses

There is no agent-trace replay subsystem. Runtime activity consists of bounded
HTTP PoC templates and the fix agent's syntax check/Git operations. The latter
now use argument arrays and temporary syntax files. Active HTTP replay remains
an uncontrolled egress boundary (G-02), and Git hooks remain an execution
boundary (G-04).

### SSRF and network egress

The scanner has multiple outbound HTTP paths and follows redirects. There is
no target-origin, DNS/IP, or redirect policy in the shared HTTP client, so G-02
remains open. The test suite used mocked fetch for the timeout regression and
did not contact an external host.

### Analytics and data exposure

PostHog is disabled unless `POSTHOG_API_KEY` is configured, but the opt-in path
still sends target host/path and unredacted error/metadata fields (G-05).
Reports also contain source-derived findings by design; HTML encoding now
prevents those values from becoming executable markup.

### Supply chain

The final production audit is clean. The complete dependency snapshot retained
development/build/test advisories, including critical findings in the Vitest /
Tinypool toolchain and high findings in PostCSS, nanoid, and source-map-js.
Those packages are not in the 290-dependency production install represented by
`audit-2026-10-11-dependencies-prod.json`, but development servers and CI still
need the upgrades tracked in G-11.
